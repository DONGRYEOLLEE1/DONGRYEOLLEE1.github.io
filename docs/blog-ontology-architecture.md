# Vercel 기반 기술블로그의 온톨로지·추천 구현안

작성일: 2026-11-18 · 적용 대상: 기존 기술블로그 113편과 후속 게시글

## 1. 구현의 핵심

Vercel에 프론트를 배포하면서 온톨로지 기반 탐색을 운영할 수 있다. 관계를 어디에 저장하는지, 언제 계산하는지, 방문자에게 어떤 기능을 제공하는지는 각각 결정할 수 있다. 현재 블로그의 관련 글·개념 페이지는 글이 게시될 때 계산해 두는 방식이 잘 맞는다. 방문할 때마다 그래프 DB에 질의하거나 LLM을 호출할 필요는 없다.

앞선 계획의 온톨로지는 Article·Concept·Series·Project와 허용된 관계 타입을 정의한 경량 지식 모델이다. RDF·OWL 추론 엔진을 갖춘 정식 의미 웹 시스템을 이미 구축했다는 뜻은 아니다. 이름·별칭·상하위 개념은 SKOS의 모델을 참고할 수 있지만 별도 매핑 없이 표준 호환을 선언하지 않는다.

| 구분 | 역할 | 이 블로그의 예 |
|---|---|---|
| 온톨로지·스키마 | 어떤 대상과 관계를 표현할지 정의 | 글은 개념을 핵심 주제로 다루거나 실제 적용할 수 있음 |
| 지식 그래프 | 그 규칙으로 실제 데이터를 연결 | Reranking 학습 글은 재정렬을 주제로 다루고, 책등 인식 글은 재정렬을 적용 |
| 그래프 DB | 연결 데이터를 저장·갱신·질의하는 저장 기술 | 필요 시 Neo4j 같은 외부 DB 사용. 관계를 파일이나 관계형 테이블로 저장할 수도 있음 |
| GraphRAG | 그래프를 검색 문맥으로 활용해 질문에 답하는 RAG 구성 | 여러 글을 연결해 ‘내 OCR 연구에서 평가 방식은 어떻게 달라졌나?’를 근거와 함께 답하기 |

그래프를 화면에 그리는 기능과 GraphRAG는 구별해야 한다. Microsoft GraphRAG는 개체·관계 추출, 커뮤니티 구조·요약과 질문 시 검색을 결합한다. 관련 글 링크와 관계 이유를 보여주기 위해 이 전체 질의응답 파이프라인을 도입해야 하는 것은 아니다. [S1]

## 2. 첫 구현의 배포 구조

| 단계 | 실행 위치·시점 | 실제 작업·산출물 |
|---|---|---|
| 콘텐츠 작성 | 로컬·Git | Markdown 본문, 영구 글 ID, 공개 상태, 짧은 설명 |
| 개념·관계 보완 | 게시 전 로컬 또는 CI | 기존 개념 사전에서 후보 추출, 별칭 통합, about/applies 역할 확인. 원문 링크에서 cites 추출 |
| 원본 확정 | Git의 YAML/JSON | concepts·series·projects·글별 conceptRefs·수동 관계·제외 항목. 원본을 한 곳에서 편집 |
| 배포 빌드 | Vercel 빌드 또는 사전 CI | 공개 글만 읽고 참조·계층 순환·기존 주소를 검증. 전체 공개 집합에서 관련 글을 다시 계산 |
| 배포 산출물 | 정적 HTML·JSON | 글 본문, 주제 페이지, 글별 관련 글 ID·관계 이유, 미니 그래프 데이터, 검색 인덱스 |
| 방문 | Vercel의 정적 배포 | 이미 계산된 HTML·글별 JSON을 읽어 표시. 클릭·포커스·선택은 브라우저에서 처리 |

예를 들어 신규 OCR 글이 추가되면 그 글에서 확인한 `korean-ocr`·`reranking` 개념과 applies 관계를 반영한다. 빌드가 새 글과 기존 공개 글의 연결을 다시 계산하므로 신규 글뿐 아니라 기존 Reranking 글의 관련 목록도 갱신될 수 있다. 새 글만 계산하고 기존 목록을 그대로 두면 ‘자동 추적’의 절반만 구현한 셈이다.

개념·링크·어휘 기반 계산은 외부 API 없이 빌드에서 재현할 수 있다. 의미 연결을 보완하려고 임베딩이나 LLM 추출을 도입하면 변경 글만 별도의 로컬·CI 작업에서 처리하고, 검증한 특징·관계 데이터를 빌드에 전달한다. 대형 모델 다운로드나 장시간 전체 추출을 매번 Vercel 빌드의 필수 단계로 만들지 않는다.

## 3. 어떤 부분이 자동인가

| 작업 | 첫 운영의 방식 | 자동화의 경계 |
|---|---|---|
| 내부 글 링크 | 본문에서 실제 링크 추출 | 링크가 있다는 사실만 자동 기록. 연구 선후관계로 바꾸지 않음 |
| 개념 후보 | 사전의 이름·별칭과 본문을 대조 | 단어가 등장했다는 사실만으로 핵심 주제·적용 여부를 확정하지 않음 |
| 새로운 개념·관계 | 사람이 확인하거나 LLM이 구조화 후보 제안 | LLM 제안에는 원문 근거를 붙이고 검토한 뒤 원본에 반영 |
| 관련 글 순위·이유 | 승인된 개념·어휘·링크·프로젝트로 계산 | 수동으로 모든 edge를 그릴 필요는 없지만 품질 평가는 필요 |
| 화면·기존 글의 추천 갱신 | 변경 게시 후 전체 공개 집합 재계산·배포 | 삭제·비공개 글은 추천·검색·sitemap에서도 함께 제외 |

따라서 기존 계획은 사람이 아무 입력도 하지 않는 완전 자동 온톨로지 생성이 아니다. 핵심 개념과 사실 관계는 확인하고, 관련 글의 계산·기존 목록 갱신·화면 생성은 자동화하는 구조다. 완전 자동 추출을 원하면 추출 모델·근거 검증·오류 수정 흐름을 별도의 기능으로 설계해야 한다. 그래프 DB를 추가하는 것만으로 이 의미 검증 문제까지 해결되지는 않는다.

## 4. 실제 글의 연결 예

Reranking 학습 글은 Cohere의 재정렬을 설명한다. 책등 인식 글은 RapidFuzz·규칙 기반으로 후보를 다시 정렬한다. 두 글은 공통 개념 `reranking`으로 연결할 수 있고 카드에는 ‘검색 재정렬을 적용한 사례’라고 표시할 수 있다. 두 글이 같은 모델을 썼다거나 한 글이 다른 글의 후속 연구라는 관계는 기록하지 않는다.

이때 필요한 질의는 ‘현재 글이 다루는 개념을 확인하고, 같은 개념을 다루거나 적용한 공개 글을 찾아 우선순위를 정한다’다. 현재 규모에서는 배열·맵·인접 목록으로 빌드 시 계산할 수 있다. 저장 형식을 JSON으로 선택해도 관계 데이터가 사라지는 것은 아니다.

## 5. 그래프 DB와 GraphRAG를 추가할 조건

| 요구가 생겼을 때 | 추가하는 구성 | Vercel과의 연결 |
|---|---|---|
| 여러 사람이 웹에서 관계를 동시에 편집하고 즉시 반영 | 트랜잭션·권한·변경 이력을 갖춘 DB와 편집 API | Vercel은 UI·서버 API, 데이터는 외부 관리형 DB에 보관 |
| 방문자가 조건을 바꾸며 복잡한 다중 홉 경로를 즉시 탐색 | 그래프 DB 또는 관계형 DB의 그래프 질의 계층 | 서버 API가 DB에 질의하고 필요한 공개 결과만 반환 |
| 글 전체를 종합해 근거 있는 자연어 답변 생성 | 검색·추론 API와 LLM. GraphRAG는 후보 방식 중 하나 | 프론트는 Vercel 유지. 인덱싱은 별도 작업, 질의는 서버 API 또는 별도 서비스 |
| 게시 때 갱신되는 관련 글·주제 페이지 | 현재의 파일 원본·정적 계산 | 전용 그래프 DB 없이 배포 가능 |

GraphRAG를 쓰더라도 Neo4j가 반드시 필요한 것은 아니다. Microsoft GraphRAG의 기본 인덱싱 산출물은 파일 기반 Parquet 테이블이며 임베딩은 별도 설정한 벡터 저장소로 보낸다. 공식 설정에서 output 저장 방식의 기본값도 file이다. 이는 ‘그래프를 활용한다’와 ‘전용 그래프 DB를 운영한다’가 별개 선택이라는 실제 사례다. [S2, S3]

외부 DB를 사용할 경우 DB 주소·인증 정보·추출용 API 키는 서버 설정에 두고 브라우저로 보내지 않는다. 게시 시점에만 업데이트되는 사이트라면 관계 저장소를 DB로 바꾸더라도 독자에게는 정적 산출물을 배포하는 선택을 유지할 수 있다. 동적 DB 연결과 동적 페이지 렌더링도 항상 한 묶음일 필요는 없다.

## 6. 권장 결론

현재 113편의 단일 작성자 블로그에는 Git의 개념·관계 파일, 빌드 시 관련 글 계산, 정적 HTML·JSON 배포로 시작하는 안을 권장한다. 기존 글을 한 번 정리하고 새 글의 개념·적용 관계를 확인하는 운영 부담은 정직하게 포함해야 한다. 화면 목업에서 고른 연결 예시를 자동 추출·평가까지 구현된 기능처럼 설명해서는 안 된다.

나중에 웹 편집·실시간 경로 탐색·여러 글을 종합한 질의응답이 실제 목표가 되면, 같은 글 ID·개념 ID·관계 모델을 유지하면서 저장소나 검색 계층을 확장한다. 전환 기준은 추정한 글 수가 아니라 필요한 수정·조회·응답 동작이다.

## 현재 연결한 실행 예제

화면 목업에는 실제 글 10편·개념 12개의 검토 데이터를 사용하는 생성기를 연결했다. [concepts.json](preview/knowledge/concepts.json)은 개념과 허용 관계, [article-concepts.json](preview/knowledge/article-concepts.json)은 글별 about/applies 관계, [build-related.mjs](preview/knowledge/build-related.mjs)는 전체 후보 비교·관계 이유 생성을 담당한다. 결과는 [related.json](preview/knowledge/related.json)에 기록한다.

[build-preview.mjs](preview/build-preview.mjs)를 실행하면 먼저 관련 글을 다시 계산한 다음 화면 HTML을 만든다. Reranking 글에서 책등 인식 글을 선택하면 `적용 사례 · Reranking`이라는 생성된 관계 이유가 표시된다. 구체적으로 연결할 근거가 없는 글에는 임의 추천을 채우지 않는다. 새 OCR 글을 넣으면 기존 KoDistill 글의 추천도 바뀌는 검증을 포함해 10개 경계 검증을 통과했다.

이 예제는 파일 기반 관계 모델과 빌드 계산이 작동한다는 증명이다. 현재 원문의 개념 추출을 LLM으로 자동화하거나 113편 전체를 이전한 것은 아니다. 정식 구현에서는 전체 글의 개념 검토·의미 검증·추천 품질 평가와 배포 연결을 이어서 수행한다.
