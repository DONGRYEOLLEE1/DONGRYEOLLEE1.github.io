# 연관 글 그래프 구현 계획

수정일 2026-11-20 · 저장소 `DONGRYEOLLEE1/tech-blog` · 구현 브랜치 `feat/related-embeddings` · 파일럿 보고서 `docs/phase2a-pilot.md`

## 목표와 현재 상태

글 오른쪽 그래프에 근거를 확인할 수 있는 연관 글을 0~4편 표시한다. **Phase 2A를 113편 전체에 적용했다(2026-11-20).** 추천은 `content/related/<글 ID>.json`에 글마다 저장하고, 빌드는 API 키 없이 이 파일을 검증해 표시한다. 검증에 실패했거나 파일이 없는 글만 `tools/knowledge/related.mjs`의 규칙 추천으로 돌아간다.

### 적용 전 검증 결과 (고정 모델 실측)

**새 글 발행 시나리오.** 가상의 글 4편을 하나씩 넣어 동기화했다. 기대·금지 연결은 실행 전에 정했다.

| 가상 글 | LLM 호출 | 기대 연결 적중 | 금지 연결 |
| --- | --- | --- | --- |
| 주제가 맞는 한국어 글(작성자 개념 없음) | 8회 (2 + 6) | 3/3 | 0건 |
| 무관한 글 | 2회 (2 + 0) | 추천 없음 | 0건 |
| OCR·reranking을 지나가며 언급만 한 글 | 4회 (2 + 2) | 추천 없음 | 0건 |
| 관련 글이 모두 한국어인 영문 글 | 13회 (2 + 11) | 3/3 | 0건 |

재실행하면 호출이 0회였고, 새 글을 지우면 그 글의 파일이 삭제되고 영향받은 글만 다시 호출됐다.

**전체 113편 판정.** 독립 심사 에이전트가 원문을 읽고 모든 추천을 판정했고, 문제로 판정된 항목은 다른 에이전트가 다시 확인했다. 심사자는 작성자가 아니므로 수치는 참고값이다.

| | 2A 첫 실행 | 2A 발행본 | 현행 규칙 |
| --- | --- | --- | --- |
| 추천 수 | 243 | 233 | 367 |
| 이어 읽을 구체적 이유 있음 | 65.0% | 68.7% | 41.1% |
| 넓은 분야만 같음 | 30.0% | 31.3% | 38.4% |
| 무관 | 4.9% | 0% | 20.4% |
| 이유 문장의 사실 오류 | 4.1% (10건) | 0건 | 해당 없음 |

글 단위로는 2A 목록이 나은 글 66편, 비슷한 글 25편, 규칙 목록이 나은 글 22편이었다. 규칙이 나은 경우는 대부분 2A가 같은 연재나 후속 글을 빠뜨린 경우다.

첫 실행과 발행본의 차이는 판정 결과를 다음 세 가지로 반영한 것이다.

- 무관하거나 이유가 틀린 22쌍을 `content/knowledge/overrides.json`의 `excludes`에 등록했다. 작성자가 무관하다고 판단한 책등 인식 ↔ KoDistill도 여기에 있다.
- 추천은 맞지만 이유 문장이 틀린 4쌍은 `content/knowledge/reasons.json`에 고친 문장을 등록했다. 이 문장이 모델 문장을 대신한다.
- 명시적 연재의 이전·다음 글은 모델의 선택과 무관하게 목록에 남긴다.

**남은 위험.** 새 글을 발행하면 첫 실행과 같은 비율(무관 약 5%, 이유 오류 약 4%)로 문제가 생길 수 있다. 발행할 때 `content/related/`의 변경분을 읽고, 틀린 연결은 `excludes`, 틀린 문장은 `reasons.json`으로 고친다. 영문 글의 이유가 일본어로 나온 적이 있어 한글이 아닌 이유는 코드가 거부한다.

Vercel 빌드와 독자 방문 시점에는 호출하지 않는다. 모델 ID·추론 설정·프롬프트·스키마 버전은 아래 입력 해시에, 임베딩 프로필은 벡터 캐시 키에 포함한다. `tools/knowledge/model.mjs`의 기본 모델은 `openai/gpt-6-luna`이고 `seed: 7`, `reasoning.effort: low`, 출력 한도 8,000토큰으로 호출한다. `RECOMMENDATIONS_API_BASE`로 다른 OpenAI 호환 엔드포인트를 쓰면 `temperature: 0`으로 호출한다.

OpenRouter 카탈로그(2026-11-20 확인) 기준으로 `openai/gpt-6-luna`는 입력 $0.10, 출력 $0.50, `google/gemini-embedding-2`는 $0.20이다(100만 토큰당). 재정렬 입력은 평균 약 1.9만 자, 관계 추출 입력은 평균 약 1.1만 자여서 새 글 1편 발행은 몇 센트에서 십수 센트, 초기 일괄 적용은 $1 안팎으로 어림한다.

## Phase 2A · 관계 추출과 추천

### 온톨로지의 노드와 관계

노드는 글(`Article`)과 개념(`Concept`) 엔티티다. 글 ID와 개념 ID는 유형으로 구분한다. `about`은 글이 해당 개념을 주제로 다룬다는 관계이고, `applies`는 글에서 그 개념을 실제로 적용했다는 관계다. 개념의 `broaderIds`는 바로 위에 있는 개념의 ID를 담는다. Project는 UI와 `origin/main`에서 제거했으며 후보 계산에 쓰지 않는다.

```text
article:book-spine  ── applies ──→ concept:reranking
article:reranking   ── about   ──→ concept:reranking
concept:reranking   ── broader ──→ concept:rag
```

개념의 직접 상위 관계는 W3C SKOS를 참고한다. LLM이 추출한 글과 개념의 관계에 원문 근거를 함께 저장하는 설계는 DocRED의 관계 및 근거 문장 표기를 참고한다. 오른쪽 그래프는 이 관계를 추천 근거로 사용하고, 현재 글과 추천 글을 노드로 표시한다. [W3C SKOS §8](https://www.w3.org/TR/skos-reference/) · [DocRED, ACL 2019](https://aclanthology.org/P19-1074/)

### 1. 글 하나에서 사실을 먼저 추출한다

- `tools/content/build.mjs`에서 공개 원문 판독과 블록 추출을 공통 함수로 분리한다. 영구 ID·공개 상태·언어를 먼저 확인한다. 빌드(`!meta.conceptRefs.length` 검사)와 지식 검증기의 `conceptRefs` 최소 1개 조건은 **빈 관계 목록도 유효한 상태**로 바꾼다. 종합 계획서 §11의 ‘최소 1개’ 계약은 이 문서가 대체한다.
- 블록은 렌더된 본문의 문단·코드·표 행·목록 항목 단위이고 최대 480자다. 블록 ID는 헤딩 앵커와 하위 블록 순번으로 만든다. 첫 헤딩 앞 문단과 헤딩 없는 코드에는 글 루트 기준 ID를 부여한다. 현재 113편은 약 4,000블록(글당 평균 35개)이다.
- LLM은 글의 전체 블록과 개념 사전을 읽고 사전에 등록된 개념 ID, `about`·`applies` 역할, 근거 블록 번호를 최대 6개 반환한다. 코드가 개념 ID·역할·블록 소속을 검증한다.
- 추천에는 검토된 `conceptRefs`와, 근거 블록을 확인한 LLM 추출 역할을 합쳐 사용한다. 같은 개념에서 두 값의 역할이 다르면 검토된 값을 쓰고 검토 기록을 남긴다. 파일럿은 기준 글 3편만 추출했다. 전체 적용 때는 113편 모두 한 번씩 추출해 후보 쪽 역할에도 근거 블록을 확보한다.
- 근거는 **글 ID, 블록 ID, 원문 발췌, 블록 내용 해시**로 저장한다. 본문 수정 후에는 해시와 발췌를 다시 확인한다. 출처 앵커는 `content/related/<글 ID>.json`에만 저장하고, 화면의 출처 링크는 2A 범위에서 제외한다.

### 2. 후보와 양쪽 근거 블록을 코드로 확보한다

이 단계는 LLM을 호출하지 않는다.

1. **그래프 후보**는 구체적인 공통 개념, 본문 내부 링크와 역링크, 명시된 시리즈 순서, 작성자가 지정한 선행 작업에서 얻는다. `tools/knowledge/related.mjs`의 후보 순위와 최종 4편 제한을 분리한다. 기존 제외·고정 설정을 반영한다.
2. **어휘 후보**는 공개 글의 제목·기존 요약(`description`)·본문을 검색한다. 개념 이름과 한영 별칭으로 검색어를 확장한다. 기존 규칙에서 최종 4편 제한만 풀었을 때 113편 중 79편은 후보가 10편 미만이었고, 그중 11편은 0편이었다.
3. **임베딩 후보**는 기준 글의 블록 벡터와 다른 글의 블록 벡터를 코사인 유사도로 비교해 얻는다. 임베딩 단위는 근거 블록과 같다(섹션 벡터를 따로 만들지 않는다). 입력은 글 제목 + 상위 헤딩 + 블록 본문이다. 글 쌍 점수는 기준 글 블록별 최고 유사도의 상위 3개 평균을 잠정값으로 쓴다.
4. 고정 글을 먼저 넣고 세 순위에서 번갈아 가져와 글 ID로 중복을 제거한다. 현재 글과 비공개·제외 대상을 걸러내고 **최대 15편**에서 멈춘다. 유사도는 소수 넷째 자리로 반올림하고 동점은 글 ID 순으로 정해 두 서버의 결과가 같게 한다.
5. **근거 블록**은 후보마다 양쪽에서 최대 3개씩 고른다. 직접 링크가 있는 블록과 검증된 관계의 근거 블록을 먼저 넣고, 나머지는 기준 글·후보 글 블록 쌍의 임베딩 유사도가 높은 순으로 채운다. 한쪽이라도 블록이 없으면 후보에서 뺀다. 파일럿에서 Reranking → 책등 인식이 서문 블록을 근거로 골라 재채점 절을 놓친 문제를 이 단계에서 고친다.
6. 3~5의 수치 규칙(상위 3개 평균, 블록 3개)은 잠정이다. 4/5를 낸 임베딩 실험의 코드가 남아 있지 않으므로, 고정 모델 재측정 때 이 규칙으로 다시 측정하고 설정을 파일럿 보고서에 기록한다.

**블록 임베딩 캐시.** 키는 (임베딩 프로필, 블록 입력 해시)다. 프로필은 공급자·모델 ID·차원·블록 분할 규칙 버전이다. 두 발행 서버가 같은 캐시를 읽고 없는 키만 API에 요청한다. 후보 순서가 벡터 값에 좌우되므로 공유 캐시는 비용 절감보다 두 서버의 결과를 일치시키는 장치다. 저장 위치는 Supabase pgvector로 확정했다(113편 × 약 35블록 × 768차원은 10MB 안팎). 벡터는 Git, Vercel 빌드, 브라우저에 두지 않는다. 프로필이 바뀌면 전체를 다시 임베딩하고 후보를 재계산한 뒤, 후보나 근거 블록이 달라진 기준 글만 재정렬한다.

### 3. 글 쌍의 추천을 판단하고 검증한다

기준 글당 한 요청에 후보와 근거 블록을 묶는다. LLM은 후보 중 이어 읽을 만한 글을 순서대로 최대 4편 반환한다. 각 항목에는 대상 ID, 추천 관계 유형, 이유 한 줄, 양쪽 근거 블록 번호가 들어간다. 발췌 원문과 해시는 코드가 붙인다. 코드는 공개 ID·자기 참조·중복·후보별 허용 관계 유형·블록 번호 범위를 검증한다. 표의 유형은 **독자에게 추천하는 이유**다. 저자가 다른 연구를 인용하거나 확장했다는 사실은 원문이 그 대상을 명시할 때만 기록한다.

| 관계 유형 | 현재 글에서 본 추천 글의 역할 |
| --- | --- |
| `concept_explanation` | 현재 글에서 사용한 개념이나 방법의 원리를 설명한다. |
| `application_example` | 현재 글이 설명한 개념을 실제로 구현하거나 적용한다. |
| `evaluation_comparison` | 현재 글과 비교할 만한 평가 조건·지표·실패 사례를 보여준다. |
| `related_method` | 같은 문제나 처리 단계에 구체적으로 연결되는 방법을 다룬다. |

예를 들어 **책등 인식 → Reranking**은 책등 글의 후보 재채점 절과 Reranking 글의 원리 설명에 근거해 `concept_explanation`이 될 수 있다. 반대로 **Reranking → 책등 인식**에서는 `application_example`이 된다. 두 방향의 추천과 근거는 각각 판단한다.

**이유 문장의 사실성.** 2A는 종합 계획서 §13의 ‘이유는 템플릿으로만 생성하고 LLM 제안은 사람이 검토한 뒤 공개한다’는 원칙을 대체한다. 공개 조건은 코드의 구조 검증이고, 이 검증은 이유 문장이 사실인지 보장하지 않는다. 저장본의 `verified`는 구조 검증 통과만 뜻한다. 파일럿에서는 KoDistill을 ‘브라우저에서 OCR을 실행한다’고 틀리게 설명한 추천이 구조 검증을 통과했다. 대책은 다음과 같다.

- 프롬프트에서 선택한 발췌에 없는 사실(실행 환경, 모델명, 수치)을 이유에 쓰지 못하게 한다.
- 이유 문장을 다시 확인하는 **검증 호출은 채택하지 않는다**(2026-11-20 결정). 재정렬 1회가 추천과 이유를 함께 내고 LLM 호출 수는 늘지 않는다.
- 고정 모델 재측정에서 이유를 발췌가 지지하는 비율을 작성자 판정으로 기록한다. 이 비율이 낮으면 이유 문장을 버리고 관계 유형별 고정 문구와 양쪽 발췌만 표시하는 방식으로 바꾼다. 이 전환도 호출 수를 늘리지 않는다.

### 4. 발행 결과와 실패 처리를 정한다

| 데이터 | 역할 |
| --- | --- |
| `content/related/<글 ID>.json` | Git에 커밋할 발행 결과. 글마다 파일 하나다. 스키마 버전·모델·추론 설정·임베딩 프로필, 그 글의 사실과 근거, 추천 순서·상태·LLM에 전달한 후보와 근거 블록 목록·입력 해시를 담는다. 전역 발행본 해시는 두지 않는다. |
| `generated/registry.json` | Astro 빌드가 기존 시리즈 순서와 주제 데이터를 조합하고, 추천을 화면에 필요한 대상 ID·이유로 투영한다. 작성자 고정(pins)은 LLM 결과보다 앞에 두고 합쳐서 4편으로 자른다. `RelatedArticle.score`는 선택 필드로 바꾼다. |
| 브라우저의 `site-data` | `BaseLayout.astro`가 모든 글의 메타데이터를 각 페이지에 넣으므로 추천 ID와 이유만 직렬화한다. 후보 전체·발췌·입력 해시는 발행 단계에만 둔다. |
| 블록 임베딩 캐시 | 위 2절의 공유 캐시. 발행 서버만 읽고 쓴다. |

- 모델이 근거 부족을 명시하고 유효한 빈 배열을 반환하면 성공한 보류(`abstained`)로 저장한다. 후보가 0편이면 호출하지 않고 빈 목록을 저장한다.
- **API 실패, 출력 형식 오류, 출력 잘림, 검증 실패**는 실행 안에서 재시도하지 않는다. 해당 글을 `fallback`으로 저장하고 종료 코드 2로 알린 뒤, 다음 동기화에서 그 글만 다시 호출한다. 이때 양쪽 근거가 여전히 유효한 직전 결과가 있으면 재사용하고, 없으면 그 글에 한해 현행 규칙 추천을 표시한다. 관계 추출이 실패한 글은 근거 블록이 그대로인 이전 관계를 유지한 채 `fallback`으로 저장한다(실패 한 번이 관계를 지워 다른 글의 재정렬을 유발하지 않게 한다). 삭제·비공개 글을 가리키는 연결은 모든 경로에서 제거한다.
- 한 단계(관계 추출 또는 재정렬)의 첫 호출 3건이 모두 글과 무관한 사유(4xx 거부, 연결 불가)로 실패하면 그 단계를 중단하고 공급자 응답 본문과 함께 종료 코드 1로 끝낸다. 이 경우 `fallback` 파일을 쓰지 않는다. 429·5xx·시간 초과는 일시 오류로 보고 글별 `fallback`으로 기록한다.
- 두 발행 서버는 `npm run recommendations:sync`로 현재 Git 작업트리의 결과를 생성하고 원문과 결과를 함께 커밋한다. 동기화는 글의 호출이 끝나는 대로 그 글의 파일을 쓰고, 공개 글이 아닌 파일은 지운다. 결과가 글별 파일이므로 두 서버가 같은 글의 파일을 바꾼 경우에만 병합이 충돌한다. 충돌하면 어느 한쪽을 택하고, 충돌 여부와 관계없이 병합 트리에서 동기화를 다시 실행한다. 입력 해시가 일치하는 글은 재사용되고, 두 새 글이 서로의 후보에 영향을 준 글만 다시 호출된다.
- Vercel 빌드와 `recommendations:check -- --offline`은 API 키와 벡터 없이 동작하며 후보를 재계산하지 않는다. 글마다 저장된 후보·근거 블록 목록을 기준으로 블록 내용 해시, 공개 ID, 관계 유형, 저장된 목록으로 계산한 입력 해시를 대조한다(`auditRecord`). 검증에 실패했거나 파일이 없는 글은 **그 글만** 현행 규칙 추천으로 발행한다. 다만 쌍의 관계 유형은 양쪽 글의 저장된 관계로 다시 계산하므로, 한 글의 관계가 사라지면 그 관계에 기대던 상대 글의 입력 해시도 달라진다. 수정된 글의 관계는 근거 블록이 그대로인 것만 계속 쓰므로 근거와 무관한 수정은 다른 글에 영향을 주지 않는다. 근거 블록 자체가 바뀌었거나 파일을 읽을 수 없으면 그 관계에 기대던 글도 함께 규칙 추천으로 돌아간다. 빌드는 결과를 한 줄로 요약하고 `generated/related-report.json`에 기록한다.
- `npm run recommendations:check`는 벡터 캐시로 후보와 근거 블록까지 다시 계산해 저장된 입력 해시와 비교하고, 빌드와 같은 글별 검증도 함께 돌린다. 낡았거나 빌드에서 무효가 될 글, 공개 글이 아닌 추천 파일이 있으면 목록을 출력하고 종료 코드 1로 끝난다. LLM은 호출하지 않으며, 캐시에 없는 블록이 있으면 임베딩이 필요하다고 알리고 실패한다.
- `recommendations:sync`의 옵션: `--dry-run`은 호출 대상 글과 이유만 출력하고 파일을 쓰지 않는다. `--only id1,id2`는 관계 추출과 재정렬을 지정한 글로 제한한다(후보는 전체에서 찾는다). 새로 추출한 관계 때문에 대상 밖 글의 저장 해시가 맞지 않게 되면 그 글 목록을 알리고 종료 코드 1로 끝나므로, 이어서 전체 동기화를 실행한다. `--reextract`는 전 글의 관계를 다시 추출한다. `--json <경로>`는 요약과 재정렬된 글·이유(`new`, `candidate-set`, `evidence`, `model`, `fallback-retry`)를 기록한다.
- 빌드 검증은 저장된 목록이 현재 원문과 맞는지만 본다. 새 글 때문에 후보가 달라진 글은 빌드에서 걸리지 않으므로, 푸시·병합 전에 `recommendations:check`를 실행한다.

### 5. 새 글 발행 시 갱신

글별 입력 해시에 의한 재사용은 파일럿에 이미 구현돼 있다. 새 글 X를 발행하면 다음 순서로 처리한다.

1. X의 블록을 추출하고 X의 블록만 임베딩한다. 기존 글의 벡터는 캐시에서 읽는다.
2. X의 관계를 추출한다. **LLM 1회.**
3. X를 포함한 전체 공개 글에서 모든 기준 글의 후보 15편과 근거 블록을 코드로 다시 계산한다. LLM 0회.
4. 기준 글마다 재정렬 입력 해시를 직전 발행의 해시와 비교한다. LLM 0회.
5. X의 후보를 재정렬한다. **LLM 1회.**
6. 해시가 달라진 기존 글 k편을 재정렬한다. **LLM k회.** 나머지는 직전 결과를 재사용한다.
7. 바뀐 `content/related/` 파일을 원문과 함께 커밋하고, Vercel이 글별로 검증해 정적 그래프로 배포한다.

| 해시 | 포함하는 입력 | 사용처 |
| --- | --- | --- |
| (발행본 해시) | 두지 않는다. 글별 파일의 두 입력 해시와 인용의 블록 내용 해시가 그 역할을 한다. | 빌드가 글마다 저장된 후보·근거 목록으로 입력 해시를 다시 계산해 대조 |
| 글별 관계 추출 입력 해시 | 해당 글의 제목과 블록 내용 해시, 작성자가 입력한 `conceptRefs`, 모델·추론 설정·프롬프트 | 같으면 이전 추출 결과를 재사용. 개념 사전의 추가나 별칭 수정은 기존 글의 재추출을 유발하지 않는다. 저장된 관계의 개념이 사전에서 사라진 글은 다시 추출한다. 새 개념을 기존 글에 반영할 때는 `--reextract`로 재추출한다. |
| 글별 재정렬 입력 해시 | 기준 글, **LLM에 실제 전달한 후보(최대 15편)의 ID 집합**, 후보별 제목과 전달한 관계·근거 블록 ID와 내용 해시, 모델·추론 설정·프롬프트 | 이전 성공·보류 결과와 같으면 재사용하고 달라진 글만 재정렬 |

**기존 글이 다시 평가되는 조건**은 세 가지다. X가 그 글의 후보 15편 안에 들어온 경우, X 때문에 다른 후보가 15편 밖으로 밀려난 경우, 같은 후보인데 선택된 근거 블록이나 그 내용이 달라진 경우다. 이전에 `fallback`이던 글도 다시 호출한다. 후보 15편 안의 순서만 바뀐 것과 15편 밖의 순위 변동은 재호출 사유가 아니다. 파일럿 구현은 후보 순서까지 해시에 넣어, 어휘 IDF가 전체 글 수에 따라 흔들리면 X와 무관한 글까지 다시 호출했다. 현재 구현은 후보를 ID로 정렬해 해시하므로 순서는 영향을 주지 않는다. 스키마 버전은 해시가 아니라 파일의 `version`으로 구분한다.

**LLM 호출 횟수.** 새 글 1편 발행 시 `관계 추출 1 + 새 글 재정렬 1 + 기존 글 재정렬 k = 2 + k`회다.

| 경우 | LLM 호출 |
| --- | --- |
| 새 글 1편 발행 | 2 + k |
| 최악(모든 기존 글의 후보가 바뀜) | 2 + N. N은 기존 공개 글 수이며 113편이면 115회 |
| 초기 일괄 적용, LLM 모델·프롬프트·스키마 변경 | 2N. 113편이면 226회 |
| Vercel 빌드, 독자 방문 | 0 |

파일럿 코드(그래프·어휘 후보, 임베딩 없음)로 글 9편을 하나씩 빼고 넣어 본 모의 계산에서 k는 현재 해시 정의로 17~46편, 순서를 해시에서 빼면 12~28편, X가 후보에 들어온 글만 세면 7~22편이었다. 임베딩 후보를 넣은 뒤의 k는 재측정 때 기록한다. 임베딩 API는 X의 블록만 배치로 1요청 보낸다(초기 일괄은 약 4,000블록).

### 2A 완료 기준과 전체 적용 판단

- [ ] `openai/gpt-6-luna`로 관계 추출과 재정렬을 각 1회 실제 호출해 strict JSON 스키마와 출력 한도가 수용되는지 확인한다. 출력 잘림과 스키마 거부를 `fallback` 사유로 구분해 기록한다.
- [ ] 고정 모델 조합으로 파일럿 3편을 다시 실행해 위 표의 로컬 모델 결과와 비교한 값을 기록한다. 이 재측정 전에는 전체 적용을 판단하지 않는다.
- [ ] 작성자가 현행 추천 목록을 보지 않고 평가용 기준 글과 기대 연결·금지 연결을 정한다. 기대 연결을 현행 규칙의 출력에서 고르면 현행 규칙이 구조적으로 유리하다. 기준 글 수와 합격선은 작성자가 확정한다.
- [ ] 같은 사례로 현행 규칙 추천과 2A를 비교한다. 기대 글이 후보 15편 안에 포함되는 비율, 최종 추천의 기대 연결 적중과 금지 연결 건수, 이유를 발췌가 지지하는 비율(작성자 판정), 보류 건수를 기록한다. 기대 후보 누락은 검색 단계, 후보에 있는 글의 오선정은 재정렬 단계에서 고친다.
- [ ] 책등 인식 → Reranking과 역방향의 역할이 3절의 예시와 일치하고, 근거 블록이 후보 재채점 절을 가리킨다. 책등 인식 ↔ KoDistill은 어느 방향에도 나오지 않는다.
- [ ] 헤딩 없는 코드 글 `peft-target-modules`는 코드 블록으로 근거를 지정할 수 있다. 이미지 위주인 `mcp-meme`은 발췌할 근거가 부족하면 빈 목록을 반환한다.
- [ ] 후보와 근거가 같은 글은 다시 호출하지 않는다. 같은 후보의 근거 본문이 바뀌면 그 기준 글을 재평가한다. 저장된 보류와 재시도할 실패를 구분한다. 대상 글이 삭제·비공개되거나 근거가 사라지면 과거 연결을 재사용하지 않는다.
- [ ] 두 서버에서 서로 다른 글을 수정한 뒤 병합해도 발행 결과가 최종 원문과 일치한다. 명시적 보류, 잘못된 블록 번호, API 실패, 삭제·비공개 전환을 각각 재현한다.
- [ ] `npm run check`, `npm test`, `npm run build`와 Vercel 미리보기에서 그래프 링크, 근거 없는 빈 상태, 시리즈 순서가 정상이다. 합격선에 못 미치면 전체 적용을 보류하고 현행 규칙 추천을 유지한다.

## Phase 2B · 추가 근거 조사

첫 발췌로 판단하기 어려운 사례에서 에이전트가 후보나 추가 원문 블록을 조회하고 유지·추가·수정·제거를 제안한다. 호출 수와 읽을 블록 수에 한도를 두고, 추가로 읽은 원문의 ID·해시도 재사용 조건에 포함한다. 한도 내에서 근거가 부족하면 보류한다. 제안은 2A와 같은 검증을 거쳐 발행하고, 변경한 링크와 그 근거를 기록한다. 기준 글당 추가 호출 한도를 a회로 두면 새 글 1편의 LLM 호출 상한은 `2 + (k + 1)(1 + a)`회다.

### 2B 완료 기준

- [ ] 에이전트의 기준 글당 호출 한도와 읽을 블록 한도를 수치로 정하고, 한도에 닿으면 보류한다.
- [ ] 에이전트가 추가로 읽은 블록이 바뀌면 해당 기준 글을 재평가한다.

아래는 2026-11-18에 작성한 임베딩 단독 추천안이다. 현행 기준은 위의 Phase 2A와 2B다. 이 초안의 모델 ID(`qwen/qwen3.7-flash`), 섹션 단위 임베딩, `wiki/index.md` 요약, 유사도만으로 고르는 추천은 쓰지 않는다. 캐시 키 규칙과 글 쌍 점수식만 2A가 이어받았다.

### 1. 모델과 발행 명령

| 용도 | 초기값 제안 | 처리 단위 |
| --- | --- | --- |
| 한 줄 요약 | OpenRouter의 `qwen/qwen3.7-flash` | 추가·수정된 공개 글의 본문을 읽고 글과 같은 언어로 작성 |
| 섹션 임베딩 | OpenRouter의 `google/gemini-embedding-2`, 768차원 | 제목·섹션 제목·섹션 본문을 함께 입력 |

LLM의 한 줄 요약은 `wiki/index.md`에 넣어 글 목록을 읽는 데 사용한다. 오른쪽 그래프의 후보 검색과 순위 계산은 제목과 원문 섹션으로 만든 임베딩을 사용한다.

모델 ID와 임베딩 설정은 코드에서 바꿀 수 있게 구성한다. 두 발행 서버는 같은 설정과 Supabase 프로젝트를 사용한다. 새 명령 이름은 `npm run recommendations:sync`로 잡는다. OpenRouter 키와 Supabase 접속 정보는 각 발행 서버의 환경 변수에서 읽는다.

### 2. 섹션 추출과 Supabase 공유 캐시

1. 현재 발행할 공개 글을 읽고, 기존 글 ID와 제목 앵커를 사용해 본문을 Markdown 헤딩 기준으로 나눈다. 긴 섹션은 모델 입력 한도 안에 들어오도록 더 나눈다.
2. 실제 임베딩 입력 문자열을 해시한다. Supabase에 일치하는 레코드가 있으면 벡터를 재사용하고, 빠진 섹션만 OpenRouter에 배치로 요청한다.
3. Supabase Postgres의 `pgvector` 테이블에 아래 정보를 저장한다.

| 필드 | 용도 |
| --- | --- |
| `embedding_profile` | 공급자·모델 ID·차원·섹션 분할 규칙 버전 |
| `article_id` | 기존 레포의 영구 글 ID |
| `section_id`, `chunk_index` | 원문 앵커와 섹션 내 분할 순서 |
| `input_sha256` | 벡터를 만들 때 사용한 입력 텍스트의 해시 |
| `embedding` | `pgvector`로 저장한 768차원 벡터 |

프로필·글 ID·섹션·분할 순서·입력 해시를 함께 고유 키로 둔다. 같은 키가 이미 있으면 저장된 행을 재사용한다. 발행 작업은 현재 본문에 해당하는 해시만 조회하므로 두 서버가 같은 글의 다른 버전을 처리해도 각 버전의 캐시가 구분된다. 모델을 바꿀 때는 새 프로필로 재임베딩하고 해당 프로필의 벡터로 전체 추천을 재계산한다.

### 3. 추천 계산과 파일 출력

- 각 현재 글의 섹션을 후보 글의 섹션들과 비교한다. 현재 글의 섹션마다 후보 쪽 최고 코사인 유사도를 구하고, 그중 상위 3개를 평균해 글 쌍의 점수로 사용한다. 섹션이 3개보다 적으면 있는 값만 평균한다.
- 현재 글과 공개 대상에서 빠진 글을 후보에서 제외한다. 점수 내림차순으로 정렬하고 동점이면 글 ID 순으로 정렬한다. 초기 한국어·영어 샘플로 최소 점수를 정하고, 그 기준을 넘는 글을 최대 4편 내보낸다.
- 새 글이 들어오면 현재 공개 글 전체의 순위를 갱신한다. 벡터는 캐시에서 읽어 오므로 기존 글의 추천에도 새 글을 반영할 수 있다.

| 파일 | 발행 시 생성할 내용 |
| --- | --- |
| `wiki/index.md` | 글 ID·제목·링크·한 줄 요약. 원문 해시가 같은 글은 기존 요약 재사용 |
| `content/related.json` | 스키마 버전, 공개 글 집합의 해시, 임베딩 프로필과 글별 추천 ID·점수 |
| `generated/registry.json` | Astro 빌드에서 `content/related.json`의 글별 추천을 각 글의 `related` 필드에 합친 결과 |

`content/related.json`의 공개 글 집합 해시는 글 ID 순으로 정렬한 글별 입력 해시 목록으로 계산한다. 추천에 쓰인 제목이나 본문이 바뀌면 집합 해시도 바뀐다.

`wiki/index.md`와 `content/related.json`은 Git에 커밋한다. Astro 콘텐츠 빌드가 기존 개념·시리즈 검증과 시리즈 순서를 계산하고, 연관 글 목록은 새 추천 파일에서 가져오도록 연결한다. 추천에 이유가 있는 경우에만 글 하단의 관련 글 목록에서 그 이유를 표시한다.

### 4. 두 서버의 발행 절차

1. 발행 서버에서 원문을 추가·수정하고, 최신 `main`의 변경을 반영한다.
2. `recommendations:sync`로 요약과 추천 JSON을 생성하고, 해당 작업트리의 공개 글 집합과 결과의 해시가 일치하는지 확인한다.
3. 원문과 결과 파일을 함께 커밋한다. 그 사이 다른 서버의 글이 먼저 합쳐졌다면 최신 `main`을 반영한 작업트리에서 추천을 다시 계산한다.
4. Vercel 빌드가 커밋된 추천 ID를 실제 공개 글에 대조하고 그래프를 그린다.

동기화는 계산과 검증이 끝난 뒤 결과 파일을 교체한다. API나 DB 요청이 실패한 경우 직전 결과 파일을 유지하고, 성공한 벡터는 다음 실행에서 재사용한다.
